# Quotation alerts: backend configuration

The Quotation alerts page (`/quotations`, admins only) records the cost of maintenance work done at the office, such as electrical, plumbing or carpentry jobs. For each one it generates an invoice and tracks whether it has been paid. Unpaid quotations also appear in a card on the admin home page.

When an admin creates a quotation, every other admin sees it on their home page until they acknowledge it. Each acknowledgement is saved in `hrc_employee_response` (see [Acknowledgements](#acknowledgements)).

## Module

The SmartGateway module is **`hrc_quotations`**. It has the standard fields (`id`, `date_entered`, `date_modified`, `deleted`, `created_by`) plus the fields below. All requests go through SmartGateway with the usual `X-Api-Token` and CRM bearer token. The frontend uses `fetch`, `create`, `update` and `delete`.

## Fields

17 custom fields. The frontend sends every field on create. On update it sends every field except `admin_id`. Empty optional fields are sent as `""`.

| Field | Type | Required | Values and rules |
| --- | --- | --- | --- |
| `name` | String (255) | Yes | Short title of the work, e.g. "Light fixing, 2nd floor". Shown as the invoice line item. |
| `quotation_number` | String (20) | Yes | Generated by the frontend on create, e.g. `QT-2610-7K3F` (year, month, then 4 random characters). Never changes after create. Should be unique. |
| `category` | Enum or string | No | One of `Electrical`, `Plumbing`, `Carpentry`, `Painting`, `Civil work`, `Cleaning`, `IT & network`, `AC & appliances`, `Other`. |
| `work_date` | Date (`YYYY-MM-DD`) | No | Day the work was done. Defaults to the day it was entered. Used by the time filter. |
| `work_location` | String (255) | No | Where in the office, e.g. "Conference room, 2nd floor". |
| `description` | Text | No | Full description of the work. Plain text; line breaks are kept. |
| `worker_name` | String (255) | Yes | Name of the person who did the work (the payee). |
| `worker_company` | String (255) | No | Who the worker belongs to: agency, shop or area. |
| `worker_phone` | String (20) | No | Contact number: 7–20 characters of digits, spaces, `+`, `-`, `(`, `)`. |
| `amount` | Decimal (12,2) | Yes | Amount in INR, greater than 0. Sent as a string such as `"4500"` or `"1200.5"`, without commas or currency signs. |
| `payment_status` | Enum | Yes | `unpaid` (default) or `paid`. |
| `payment_method` | Enum | When paid | `Cash`, `UPI`, `Bank transfer`, `Cheque`, `Card`, `Other`. Empty when unpaid. |
| `paid_on` | Date (`YYYY-MM-DD`) | When paid | Payment date. Empty when unpaid. |
| `payment_reference` | String (100) | No | Transaction, UPI or cheque number. Empty when unpaid. |
| `payment_by_id` | Relate / ID (36) to `hrc_employees` | When paid | Employee id of the admin who made the payment, chosen from a dropdown of all admins. Defaults to the admin recording it. Empty when unpaid. |
| `notes` | Text | No | Any other information, e.g. warranty or materials used. |
| `admin_id` | Relate / ID (36) to `hrc_employees` | Yes, on create | Employee id of the admin who created the quotation (`userInfo.id` from login). Sent only on create, so edits never change it. Used to see who created each quotation. |

### Names of who created and who paid

The table has **Created by** and **Paid by** columns, and the invoice shows both people. As with other relate fields, such as `approved_by_id` on leaves, return the related employee's name next to each id in fetch responses:

| Id field | Name field to return |
| --- | --- |
| `admin_id` | `admin_id_name` |
| `payment_by_id` | `payment_by_id_name` |

If a name is missing, the frontend looks the id up in the admin list below.

### Admin list

The "Paid by" dropdown lists all admins. The frontend fetches every employee, sorted by first name on the server:

```json
{ "action": "fetch", "module": "hrc_employees", "order_by": "first_name", "order_dir": "ASC", "page": 1, "per_page": 100 }
```

It then keeps employees whose `status_id_name` is `Admin` (case-insensitive). Each admin is shown as `first_name last_name (email1)`.

### Date column

The table's Date column shows `date_entered_time_ago` (e.g. "5 days ago"), with the work date under it. Return this field with each quotation in fetch responses.

## Requests the frontend makes

### List (page and home card)

Sorted on the server, newest first. The frontend pages through `total_pages` and hides records with `deleted = "1"`.

```json
{
  "action": "fetch",
  "module": "hrc_quotations",
  "order_by": "date_entered",
  "order_dir": "DESC",
  "page": 1,
  "per_page": 100
}
```

With the time filter (This month, Last month, Last 3 months, This year or Custom), it adds a range on `work_date`. Both ends are inclusive.

```json
{
  "action": "fetch",
  "module": "hrc_quotations",
  "date_range": "custom",
  "date_field": "work_date",
  "date_from": "2026-10-01",
  "date_to": "2026-10-31",
  "order_by": "date_entered",
  "order_dir": "DESC",
  "page": 1,
  "per_page": 100
}
```

A custom range with only one end uses `0000-01-01` or `9999-12-31` for the open end. Records with no `work_date` should match by their `date_entered` date, if possible.

### Create

```json
{
  "action": "create",
  "module": "hrc_quotations",
  "data": {
    "name": "Light fixing, 2nd floor",
    "quotation_number": "QT-2610-7K3F",
    "category": "Electrical",
    "work_date": "2026-10-26",
    "work_location": "Open office, 2nd floor",
    "description": "Replaced 6 LED tube lights and fixed a loose connection in the main switchboard.",
    "worker_name": "Ramesh Kumar",
    "worker_company": "Sharma Electricals, Sector 62",
    "worker_phone": "+91 98110 45230",
    "amount": "4500",
    "payment_status": "unpaid",
    "payment_method": "",
    "paid_on": "",
    "payment_reference": "",
    "payment_by_id": "",
    "notes": "",
    "admin_id": "<employee id of the logged-in admin>"
  }
}
```

The response must include `success: true` and the new record's id as `id`, `record.id` or `data.id`.

### Edit (also how a payment is added)

Same `data` as create, without `admin_id`. A payment is added by editing the quotation and marking it paid. The same update then carries the payment fields:

```json
{
  "action": "update",
  "module": "hrc_quotations",
  "id": "<quotation id>",
  "data": {
    "...": "all other fields except admin_id",
    "payment_status": "paid",
    "payment_method": "UPI",
    "paid_on": "2026-10-27",
    "payment_reference": "UPI 4012 7788 1290",
    "payment_by_id": "<employee id of the admin who paid>"
  }
}
```

### Delete

Delete first removes the quotation's acknowledgements from `hrc_employee_response`, one at a time, so none is left pointing at a missing quotation. It then deletes the quotation:

```json
{ "action": "delete", "module": "hrc_employee_response", "id": "<acknowledgement id>" }
{ "action": "delete", "module": "hrc_quotations", "id": "<quotation id>" }
```

If an acknowledgement can't be deleted, the quotation is left in place and the admin is asked to try again.

## Acknowledgements

A quotation needs acknowledging by every admin except the one who created it (`admin_id`). Until an admin acknowledges it, it appears in an alert on their home page with an **Acknowledge** button. The Quotation alerts table has an **Acknowledged by** column, and the invoice lists who has acknowledged it and who it is still waiting on.

Each acknowledgement is one record in the existing **`hrc_employee_response`** module, the same module that holds system-alert answers. It uses these fields:

| Field | Type | Values and rules |
| --- | --- | --- |
| `alert_id` | Existing field | The acknowledged quotation's id. For system-alert answers this field holds the alert id; for acknowledgements it holds the quotation id. |
| `employee_id` | Relate / ID (36) to `hrc_employees` | Employee id of the admin who acknowledged it. Return `employee_id_name` with it. Add this field if the module doesn't have it yet. |
| `description` | Existing field | Always `acknowledged`. The backend only accepts system-alert answers (`seen`, `acknowledged`, `yes`, `no`) here. |
| `name` | Existing field | Always starts with `Quotation acknowledged: ` followed by the quotation number, e.g. `Quotation acknowledged: QT-2610-7K3F`. Because `alert_id` and `description` look like a system-alert answer, this prefix is what separates acknowledgements from alert answers. The System alerts page leaves out records whose name has this prefix. |

When the record is created, `date_entered` is when the admin acknowledged.

### Create (when an admin clicks Acknowledge)

```json
{
  "action": "create",
  "module": "hrc_employee_response",
  "data": {
    "name": "Quotation acknowledged: QT-2610-7K3F",
    "description": "acknowledged",
    "alert_id": "<quotation id>",
    "employee_id": "<employee id of the logged-in admin>"
  }
}
```

The frontend never sends this for the quotation's creator, and sends it only once per admin per quotation. The server should also reject a second acknowledgement from the same admin for the same quotation.

### List

Filtered and sorted on the server, oldest first:

```json
{
  "action": "fetch",
  "module": "hrc_employee_response",
  "filters": { "description": "acknowledged" },
  "order_by": "date_entered",
  "order_dir": "ASC",
  "page": 1,
  "per_page": 100
}
```

## Server-side validation

Reject a save, with a readable `message`, when:

- `name` or `worker_name` is empty
- `amount` is missing, not a number, or not above 0
- `payment_status` is `paid` without a `payment_method` or a `payment_by_id`
- a date is not `YYYY-MM-DD`
- a create has no `admin_id`

## Access

Only admins use this module, and only admins create or read quotation acknowledgements. Employees and candidates must not be able to read or write either.
